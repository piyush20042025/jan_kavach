1. Architecture & Segregation Overview

The Mobile Scheme Follow-up Module enables field service men to track registered beneficiaries, review their government scheme eligibilities, record scheme applications, identify document bottlenecks, and capture benefit disbursement.

CRITICAL ADMIN SAFETY GUARANTEE: This module is completely independent from the web Admin Panel. Existing admin controllers, routes, views, models, and application workflows remain completely untouched. The mobile module utilizes its own dedicated service (MobileFollowupService), dedicated controller (MobileFollowupController), dedicated routes under /api/mobile/user/followup/*, and a dedicated database table (mobile_scheme_followups).

3. Authentication & Headers

All follow-up endpoints require Bearer Token authentication via the mobile_auth middleware. The token is obtained via the existing POST /auth/login endpoint.

POST /api/mobile/user/auth/login 
// Required Headers on all protected endpoints:
Authorization: Bearer <YOUR_MOBILE_AUTH_TOKEN>
Accept: application/json
Content-Type: application/json

4. Summary of API Endpoints

Method Endpoint Path Operational Purpose
GET /followup/dashboard Four primary summary cards, pending reason breakdown, and due buckets.
GET /followup/register Paginated follow-up records with search, status, and due filters.
GET /followup/beneficiaries/{id} Beneficiary profile, eligible schemes, document requirements & official URLs.
GET /followup/document-types Master dropdown list of 42 active document types for mobile forms.
GET /followup/schemes/{id}/documents Scheme-specific checklist of mandatory and optional required documents.
POST /followup/record Log follow-up action: Not Applied, Applied, Document Issue, or Complete.

7. Dedicated Database Schema: mobile_scheme_followups

Created and active on both Local and Live production MySQL databases:

CREATE TABLE `mobile_scheme_followups` (
  `id` bigint(20) UNSIGNED NOT NULL AUTO_INCREMENT,
  `beneficiary_id` bigint(20) UNSIGNED NOT NULL,
  `scheme_id` bigint(20) UNSIGNED NOT NULL,
  `field_user_id` bigint(20) UNSIGNED NOT NULL,
  `status` enum('Pending','Applied','Complete') NOT NULL DEFAULT 'Pending',
  `pending_reason` enum('Not applied yet','Application pending','Document issue','Verification pending') DEFAULT 'Not applied yet',
  `document_type_id` bigint(20) UNSIGNED DEFAULT NULL,
  `issue_type` varchar(50) DEFAULT NULL,
  `document_notes` text DEFAULT NULL,
  `application_number` varchar(100) DEFAULT NULL,
  `submission_date` date DEFAULT NULL,
  `benefit_received_date` date DEFAULT NULL,
  `next_followup_date` date DEFAULT NULL,
  `notes` text DEFAULT NULL,
  `created_by` bigint(20) UNSIGNED NOT NULL,
  `updated_by` bigint(20) UNSIGNED DEFAULT NULL,
  `created_at` timestamp NOT NULL DEFAULT current_timestamp(),
  `updated_at` timestamp NOT NULL DEFAULT current_timestamp() ON UPDATE current_timestamp(),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uniq_beneficiary_scheme` (`beneficiary_id`, `scheme_id`),
  KEY `idx_status` (`status`),
  KEY `idx_pending_reason` (`pending_reason`),
  KEY `idx_next_followup` (`next_followup_date`),
  KEY `idx_field_user` (`field_user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
